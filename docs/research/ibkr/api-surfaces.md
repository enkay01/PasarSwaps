# IBKR API options: TWS API on Trader Workstation, TWS API on IB Gateway, Client Portal Web API

Status: research finding  
Evidence checked: 2026-09-16

## Scope

This note covers the three IBKR API paths a local trading lab has to choose between: the TWS API pointed at Trader Workstation, the TWS API pointed at IB Gateway, and the Client Portal Web API. The current home of IBKR's API docs is ibkrcampus.com. I also used interactivebrokers.com, ibkrguides.com, and the InteractiveBrokers GitHub org.

I looked for authentication and 2FA, session lifecycle, paper against live, order types and asset classes, SDKs and language support, and the limits each path states about itself. I did not open a live or paper account and I did not run code against any of them, so nothing here is a measured result. Each claim carries a link to the IBKR page it came from.

I did not need community sources for any claim below. Where IBKR's docs are silent, "What still needs checking" says so instead of guessing.

## Short answer

Plan the lab around the TWS API pointed at IB Gateway. Install Trader Workstation on the same machine as well, for the first login and for checking data by hand.

- IB Gateway and Trader Workstation are the same server from the API's point of view, and IB Gateway uses about 40% fewer resources. [IB Gateway](https://ibkrcampus.com/docs/tws-api/doc/architecture/the-trader-workstation/the-ib-gateway)
- Neither one supports a headless session, so a GUI process has to hold the login either way. IB Gateway is the smaller process to keep alive. [General third party FAQ](https://ibkrcampus.com/docs/third-party-integrations/general-third-party-frequently-asked-questions)
- Autorestart covers Monday through Saturday. The only manual step in the week is re-authentication after the Saturday night server reset. [IB Gateway](https://ibkrcampus.com/docs/tws-api/doc/architecture/the-trader-workstation/the-ib-gateway)
- Order type, order conditioning, and market data access track Trader Workstation almost fully. [IBKR API home](https://ibkrcampus.com/docs)
- The disconnect modes are documented: error 502 when the socket is refused, error 507 (Java) or -1 (C#) when the reader thread breaks, plus connectionClosed and isConnected for detection. Reconnect logic is yours to write. [Establishing an API connection](https://ibkrcampus.com/docs/tws-api/doc/connectivity/establishing-an-api-connection), [Broken API socket connection](https://ibkrcampus.com/docs/tws-api/doc/connectivity/broken-api-socket-connection)
- Multi-leg orders are a first-class part of the TWS API through BAG contracts and ComboLeg objects. [Combo orders](https://ibkrcampus.com/docs/tws-api/doc/orders/place-order/combo-orders), [Spreads in the TWS API](https://ibkrcampus.com/docs/general/contracts/spread-contracts/twsapi-spreads/spreads-in-the-tws-api)

Reach for the Client Portal Web API only when you want the Client Portal's own view of an account, or when you are shipping software to other people. For a local lab it is the harder path. An individual user has to run the Java gateway, log in through a browser on the same machine, and repeat that login daily, and the docs state that IBKR does not support automating that login. [Installation and authentication](https://ibkrcampus.com/docs/web-api/authentication/cpgw/installation-authentication), [Client Portal Gateway FAQ](https://ibkrcampus.com/docs/web-api/authentication/cpgw/client-portal-gateway-faq)

The OAuth 2.0 route, the one that removes the local gateway, is limited to licensed organizations, financial advisors, and introducing brokers. A retail individual does not get it. [OAuth 2.0 introduction](https://ibkrcampus.com/docs/web-api/authentication/oauth-2/introduction)

Both paths run against the same kind of account. A paper account is opened from the live account, and the live account must be open, funded, and IBKR Pro before either API works. [Paper Trading](https://ibkrcampus.com/docs/tws-api/doc/notes-limitations/limitations/paper-trading), [Trading access for individuals](https://ibkrcampus.com/docs/web-api/trading/getting-started/trading-access-for-individuals)

## The three paths side by side

| Question | TWS API on Trader Workstation | TWS API on IB Gateway | Client Portal Web API |
| --- | --- | --- | --- |
| What runs locally | Trader Workstation plus your client | IB Gateway plus your client | Client Portal Gateway (Java) plus your client, for individual users |
| Transport | TCP socket to the local host | TCP socket to the local host | HTTPS and websocket to the gateway, then to IBKR |
| Login | Username and password typed into TWS | Username and password typed into IB Gateway | Browser login at `https://localhost:5000` |
| 2FA | IB Key, Handy Key, SMS, DSC+. The code cards are not supported | Same | Same |
| Unattended operation | Not supported. No GUI, no session | Not supported. No GUI, no session | The gateway itself is headless, but the login is not, and IBKR does not support automating it |
| Daily restart | Built to restart daily; autorestart from version 974+ | Same, and IBHK users are told to prefer it | Session lasts up to 24 hours and reauthentication is required daily |
| Forced logout | Saturday night server reset needs credentials entered again; weekly reauthentication cycle starts Monday | Same | `/iserver` is unavailable nightly around 01:00 local time by region; Web API maintenance is Saturday evening |
| Detecting and recovering a drop | error 502, error 507 or -1, connectionClosed, isConnected. Reconnect is the client's job | Same | `/iserver/auth/status` reports `authenticated`; call `/tickle` each minute; `/iserver/auth/ssodh/init` starts a new brokerage session |
| One session per username | One trading application at a time per username; extra usernames are available | Same | One brokerage session across all IBKR platforms; a read-only session sits in front of it |
| Paper against live | Log in with paper credentials; default ports 7496 live and 7497 paper; the API does not know which one it is talking to | Default ports 4001 live and 4002 paper | Separate paper username and password; there is no live or paper slider |
| Market data | Paid subscription per username. Live, frozen, delayed, and delayed frozen are selectable from the API | Same | Same subscription rules. Snapshot plus websocket top of book; history caps at 1000 data points |
| Order types | Nearly full parity with Trader Workstation | Same | Not all order types. Each order type page lists the interfaces that support it |
| Combos and multi-leg | BAG contract with ComboLeg. Price per leg only for a 2 leg NonGuaranteed order; 3 or more legs are priced as one order | Same | `conidex` string with a spread conid and a leg/ratio list. The number of legs varies by exchange |
| Asset classes | `secType` values: STK, OPT, FUT, IND, FOP, CASH, BAG, WAR, BOND, CMDTY, NEWS, FUND | Same | The docs show stocks, options, futures options, event contracts, and combos. No full coverage matrix is published |
| SDKs and languages | Python, Java, C++, C#, VB.NET. C# and VB.NET are Windows only. Delivered by the TWS API installer, not as a package | Same | REST and websocket, so any HTTP client works. Docs give Python and curl examples. No official SDK |
| Pacing | 50 orders per second. Message pacing is configurable; breaking it three times ends the session | Same | 10 requests per second per username, plus per-endpoint limits. `429` and a 10 minute penalty box |
| Main stated limits | No headless session, no account management, no fractional or cash quantity except crypto and forex, and nothing TWS cannot do | Same | Browser login and all calls on the gateway machine, no automated login, daily reauthentication |

## Facts to verify before building

| Topic | What the official docs say | Implication for the lab |
| --- | --- | --- |
| Ports | Defaults are TWS live 7496, TWS paper 7497, IB Gateway live 4001, IB Gateway paper 4002. They are defaults, not fixed values. [Synchronous connect](https://ibkrcampus.com/docs/tws-api/doc/synchronous-api/connect-start-connection) | Read the port from config, do not hard-code it, and never guess which environment a port points at |
| The API does not know paper from live | "Connections via the TWS API are not aware of the user name with which you are logged in with in your TWS. From this point of view the API makes no difference between live or paper trading." [General third party FAQ](https://ibkrcampus.com/docs/third-party-integrations/general-third-party-frequently-asked-questions) | The safety of paper mode comes from the login and the account number reported at handshake, not from the port. Check the account id at startup |
| Automated trading disclosure | IBKR asks users to certify whether API messages are submitted by an automated system, and to name the software and the external operator. [Automation and software disclosure](https://ibkrcampus.com/docs/general/market-data-subscriptions/compliance-requirements-for-api-market-data/api-user-activity-certification/automation-and-software-disclosure) | Expect a disclosure step for an unattended bot, separate from the account application |
| Paper account creation | Paper accounts are opened from Client Portal under Settings, then Account Configuration, then Paper Trading Account. New clients get one automatically; older accounts may not. Accounts are created within 24 hours. [Paper Trading Account](https://www.ibkrguides.com/clientportal/papertradingaccount.htm) | The paper account is a second username with its own password and its own account number, not a mode flag |
| Paper account funding and reset | Paper accounts start with USD 1,000,000 of Equity with Loan Value. The paper equity can be reset to up to five times the production account value. [About Paper Trading Accounts](https://www.ibkrguides.com/clientportal/aboutpapertradingaccounts.htm) | Paper results are not comparable to live results even after a good strategy run |
| Paper limitations | Documented gaps include no VWAP, Auction, RFQ, or Pegged to Market orders, simulated fills from the top of the book, limited combo trading, always simulated stops, no penny fills on US options, and no mutual fund trading. [About Paper Trading Accounts](https://www.ibkrguides.com/clientportal/aboutpapertradingaccounts.htm) | Do not treat a paper combo fill as evidence the live combo will fill the same way |
| Paper execution quality | "The Paper Trading Environment relies on more simulated technologies than the Live trading environment. As a result, certain behavior such as order execution may vary." [Paper Trading](https://ibkrcampus.com/docs/tws-api/doc/notes-limitations/limitations/paper-trading) | Keep paper and live results in separate ledgers |
| Multiple clients on one TWS | One TWS session accepts up to 32 simultaneous API client connections. Client ID 0 also sees orders from TWS and FIX; another client id can be set as the Master Client ID to see all orders. [Synchronous connect](https://ibkrcampus.com/docs/tws-api/doc/synchronous-api/connect-start-connection), [ClientId 0 and the master client ID](https://ibkrcampus.com/docs/tws-api/doc/order-management/client-id-0-and-the-master-client-id) | Decide one client id convention up front, or order and execution callbacks will be partial |
| Client Portal login blocks TWS autoreconnect | If TWS or IB Gateway shares a username with a Client Portal login during that session, it cannot automatically reconnect after the next disconnect. [Logging into multiple applications](https://ibkrcampus.com/docs/tws-api/doc/connectivity/logging-into-multiple-applications) | Use a separate username for the gateway, or accept losing unattended reconnect |
| Web API session lifetime | A session stays authenticated for up to 24 hours, resetting at midnight in New York, Zug, or Hong Kong. It times out after about 6 minutes without requests, or without `/tickle` every 5 minutes. `/tickle` every minute is recommended. [Authentication FAQ](https://ibkrcampus.com/docs/web-api/authentication/faq) | A Web API bot needs a tickle loop and a re-initialise path, on top of whatever your strategy does |
| Web API re-initialise | If the brokerage session times out while the connection is still up, `/iserver/auth/status` returns `connected: true` and `authenticated: false`, and `/iserver/auth/ssodh/init` starts a new session. [Authentication FAQ](https://ibkrcampus.com/docs/web-api/authentication/faq) | Status polling has to check both fields, not just connectivity |
| Web API order replies | Some order submissions return a reply message that must be confirmed with `POST /iserver/reply/{messageId}`. Message types can be suppressed for the brokerage session with `/iserver/questions/suppress`. [Order reply messages](https://ibkrcampus.com/docs/web-api/trading/orders/order-reply-messages), [Order reply suppression](https://ibkrcampus.com/docs/web-api/trading/orders/order-reply-suppression) | An unattended Web API order path needs reply handling or suppression, or orders stop at "are you sure" |
| Web API market data access | Off-platform API data needs an explicit subscription per username plus the Market Data API acknowledgement. Requirements include an opened IBKR Pro account and $500 USD above the cost of subscriptions. [Market data requirements](https://ibkrcampus.com/docs/general/market-data-subscriptions/market-data-requirements), [TWS data vs API data](https://ibkrcampus.com/docs/general/market-data-subscriptions/tws-data-vs-api-data) | Free data seen in TWS may not appear on the API, so check the API feed before writing a strategy against it |
| Market data type switch | The TWS API can request live, frozen, delayed, or delayed frozen data, but delayed data only works for `reqMktData` and `reqHistoricalData`, not tick data. [Delayed market data](https://ibkrcampus.com/docs/tws-api/doc/market-data-delayed/introduction) | A daily loop should record which data type each bar came from |
| Combo pricing rules | Combo orders can be priced per leg only with two legs in a NonGuaranteed order. Three or more legs must be priced as one order and must not be NonGuaranteed. [Combo orders](https://ibkrcampus.com/docs/tws-api/doc/orders/place-order/combo-orders) | A multi-leg options combo has one valid price shape, and the wrong shape is rejected |
| Web API combo encoding | A combo is sent as `conidex` in the form `{spread_conid};;;{leg_conid}/{ratio},...`. A positive ratio is a buy, a negative ratio is a sell. Leg count depends on the exchange. [Orders for combos and spreads](https://ibkrcampus.com/docs/web-api/trading/orders/orders-for-combos-spreads) | The spread conid is per currency, and US stock combos use the USD one alone |
| Order type coverage is not uniform | "Not all order types are available in both platforms." Order type pages label their examples by interface, where Python, Java, C++, C#, and VB are the TWS API and CURL is the Web API. [Order type by API](https://ibkrcampus.com/docs/general/order-types/notes-limitations/order-type-by-api) | Confirm each specific order type on the target API before designing around it |
| Fractional and cash quantity | "Interactive Brokers APIs do not support fractional or cash quantity trading with exception to Cryptocurrencies and Forex trading." [Order types, notes and limitations](https://ibkrcampus.com/docs/general/order-types/notes-limitations/introduction) | Share-level sizing only, except crypto and FX |
| Nothing beyond TWS | "If a certain feature or operation is not available in the TWS, it will not be available on the API side either." [TWS API limitations](https://ibkrcampus.com/docs/tws-api/doc/notes-limitations/limitations/introduction) | Prototype the combo in TWS first, then automate it |
| No account management | "Given the API does not support account management, certain 2FA methods are not supported." [Supported 2FA](https://ibkrcampus.com/docs/tws-api/doc/notes-limitations/supported-two-factor-authentication-2-fa) | Account settings stay a manual, Client Portal job |
| OAuth 2.0 audience | OAuth 2.0 is offered to "licensed Organizations, Financial Advisors, and IBrokers". Third parties may only seek OAuth 1.0a approval, which needs compliance review. [OAuth 2.0 introduction](https://ibkrcampus.com/docs/web-api/authentication/oauth-2/introduction), [Trading access for third parties](https://ibkrcampus.com/docs/web-api/trading/getting-started/trading-access-for-third-parties) | For a personal lab, plan on the gateway, not on OAuth |
| Official code distribution | The InteractiveBrokers GitHub org publishes one repository, `tws-api-public`, last updated in January 2018. The old `interactivebrokers.github.io` TWS API docs now show a deprecation notice pointing at IBKR Campus. [InteractiveBrokers GitHub org](https://github.com/InteractiveBrokers), [TWS API docs archive](https://interactivebrokers.github.io/tws-api/) | Treat the TWS API installer as the source of the official library, not GitHub |
| Community Python libraries | IBKR's docs acknowledge `ib_insync`, say they cannot support it, note it is built on a legacy API release and is no longer updated, and point users to `ib_async` instead. The same page says IBKR always advises using the direct TWS API implementation. [ib_insync and ib_async](https://ibkrcampus.com/docs/tws-api/doc/third-party-api-platforms/non-standard-tws-api-languages-and-packages/ib-insync-and-ib-async) | A wrapper is a dependency with no IBKR support. Decide that on purpose |

## What still needs checking

- The full order type by API matrix. IBKR says coverage differs between the TWS API and the Web API, and each order type page labels its own examples, but I found no single official table listing which order types work on which API. Each candidate order type needs a manual check.
- Whether a retail individual can ever use OAuth 2.0. The docs say OAuth 2.0 is for licensed organizations, financial advisors, and IBrokers, and that third parties may only seek OAuth 1.0a. The docs do not state in one place what a plain individual account gets, though the individual trading page implies username and password plus the gateway.
- How many legs the Web API combo order allows. The docs say the number "varies by exchange" without giving numbers.
- Whether the Web API covers every asset class the TWS API covers. The docs show stocks, options, futures options, event contracts, and combos. No coverage matrix is published.
- What happens to resting orders across the TWS daily restart and across a Web API session end. The docs describe the restart and the session timeout but do not state whether open orders survive, and neither do they state how a client should reconcile after reconnect.
- What "limited combo trading" means in a paper account. The paper trading guide uses that phrase without quantifying it.
- Whether IBKR supports any sanctioned path to unattended restart of TWS or IB Gateway beyond the built-in autorestart, including how the Saturday reset is meant to be handled without a human.
- How the 50 orders per second limit is measured and enforced, and whether it is per account, per session, or per client id. The FAQ states the number only.
- The exact behaviour when two API clients use the same client id. The docs say connecting with a client id already in use triggers an exception in the reader thread, but not what the second client sees on a retry.
- Whether IBKR documents a recommended reconnect cadence for the TWS API. The docs describe detection and say to build reconnection logic, and stop there.
- Community tooling for automatic login, such as IBC and similar projects. These are third party and unofficial, so nothing in this note rests on them. They need their own review if the lab wants true unattended startup.
